1 What is a mirror maze?

A maze is a simple setting in which to ask a difficult question: can a model turn a stream of images into a usable account of where it is, what it has already tried, and what to do next?

Mirror walls make the distinction between seeing a route and having a route unusually concrete. A passage can continue visually through a closed wall. A green goal can be visible in a reflection. A robot can appear in several places at once. To finish, the agent must enter the actual goal cell.

I built a small environment around this idea. It supports triangular, square, and hexagonal tilings, with square outer boundaries for square grids and hexagonal boundaries for the other two. The recorded model evaluations use square and hexagonal cells. The robot's orange front, blue back, and head arrow provide orientation cues.

The environment is also playable in the browser. Start with the review map hidden, then reveal it when you want to inspect a mistake. This page uses real recorded observations and trajectories throughout.

2 Three actions, a long memory

The action space is deliberately small: left, right, and forward. A turn is 90° on square grids and 60° on hexagonal grids. A forward action attempts to move to the adjacent cell center while preserving heading.

↶leftRotate one direction
↑forwardAttempt one cell
↷rightRotate one direction

A model submits a JSON action sequence. One submitted sequence is one planning decision, even when it contains many motor actions. The next turn receives the images after every attempted action, including rotations and collisions. The priority is to reach the goal in fewer planning decisions, then incur fewer collisions.

{"plan": "Follow the open corridor, then inspect the junction.",
 "actions": ["forward", "forward", "right"]}

All inference observations are lossless 1280 × 720 PNGs, with up to 10 reflections. There is no minimap, coordinate feed, shortest-path tool, or executable preview for the model. The model returns a public, brief action intention; private reasoning is not shown in the replays.

Execution, context, and timeout details

A legal sequence continues after a collision and stops when the actual goal is reached. An illegal sequence is rejected atomically, consumes one planning decision, and incurs one collision penalty.

The harness supplies the current action batch's images and retains conversation text. Images from earlier observation rounds are removed when preparing subsequent requests. If size or context limits are hit, the oldest image-containing round is removed first, retaining the latest current-state view. Text feedback remains. All deliveries and pruning are logged; the Astra extension required no image pruning.

The single-decision deadline is 3,600 seconds, including internal transport retries. A network retry does not execute another action or consume another planning decision. Interrupted runs resume their original conversation and physical state. Every committed planning decision was independently replayed against the canonical environment, and original input-image hashes were checked.

The direct API baseline maintains public user/assistant text. It does not replay opaque encrypted reasoning items. Native clients retain their own prompts and session management. These configurations are observational comparisons, with differences beyond the model name.

3 The first forty runs

The first study uses four fixed easy mazes: square and hexagonal grids, each with seeds MIRROR-042 and MIRROR-043. Side length is 7: 49 square cells or 127 hexagonal cells. Each run has a 200-decision cap.

Five models were tested with their configured native clients and with a direct API baseline, giving 40 completed runs. Native-client configurations solved 7/20; direct API configurations solved 6/20. The table shows the full four-case denominator rather than a precision that four cases cannot support.

There is a visible square/hex contrast, but it combines several factors. At the same side length, the hex maze has 2.59× as many cells, more possible headings, and a different generated layout. This study does not isolate a causal effect of tiling geometry or of mirrors.

4 Making the maze larger

I then tested GPT-6 Astra with Codex on the same two seeds at medium side length 11, with up to 500 decisions. These maps contain 121 square cells or 331 hexagonal cells. The observed Codex request settings were reasoning.effort=low and context=all_turns, matching the native default configuration used for the earlier Sol runs.

Astra solved three of four maps. Its successful hex run needed more motor actions than its failed hex run, despite using fewer than half as many planning decisions. This is one reason to inspect the trajectories alongside the completion count.

5 Why can a cautious agent still get stuck?

The failed medium hex run did not spend most of its budget hitting walls. It had zero collisions through decision 499. All 38 collisions came from the final 89-action sequence. It nevertheless stopped at the cap having visited only 206 of 331 cells.

During decisions 121–161, it added no new cell at all, staying at 38 visited cells for 41 consecutive decisions. Across the full run, 289 of its 500 sequences contained only rotations. The successful medium hex run had 24 such sequences in 246 decisions. These are descriptions of the action record, not observations of the model's hidden reasoning.

A similar pattern appears in a smaller setting. The Seed 2.1 Pro direct-API run on easy hex MIRROR-043 visited four of 127 cells, then discovered no new cell for decisions 5–200. A low collision count, a valid action sequence, and continued activity can all coexist with little exploration progress.

The two Astra hex mazes also warn against treating shortest-path length as a complete difficulty measure. The failed case has a shorter known-map optimum: 479 actions versus 500 in the successful case. Layout, sensing, and the order of exploration still matter.

6 The same model, a different conversation

GPT-6.1 Sol solved all four easy mazes with Codex, compared with one of four in the direct-API public-text-history baseline. On square MIRROR-043, Codex reached the goal at decision 49. The API run remained at 14 visited cells from decisions 26 through 170.

The action traces are consistent with a difference in maintaining and extending an exploration state. Implementation inspection also found a concrete difference: the API client keeps public text, whereas Codex carries native conversation state, including opaque reasoning items. The prompts and default settings differ too. The experiment therefore does not identify the individual causal contribution of reasoning-state retention.

Aggregate collision totals can obscure this distinction. In the Sol API cohort, 966 of 1,036 collisions (93.2%) occurred in the final decision of the three capped runs. That statistic is heavily influenced by end-of-budget action sequences, so it should not be read as a standalone measure of visual perception.

7 What does one planning decision measure?

The original interface allows an unlimited number of actions in one plan. That is convenient for known-path backtracking, but it also creates a tradeoff: an agent can exchange fewer planning decisions for much more physical execution.

This tradeoff is visible in the recorded model runs too. One capped DeepSeek-V4.1-Flash native-client run on easy hexagon 042 executed 61,169 actions in 200 decisions, with 21,971 collisions, while visiting 34 of 127 cells. It used the alternative source noted above.

To make that concrete, I added an offline protocol stress test. A program generates a pseudorandom sequence of left, right, and forward without reading an image, a wall, a position, or a goal. It submits the sequence as one decision. The host stops it if it happens to reach the actual goal.

The protocol fixes 500 action-sequence seeds, 20261104–20261603, before running the simulation. Each sequence is reused across all eight easy and medium maps. The action limits are 1,000, 10,000, and 100,000. Canonical-rule replays verify representative prefixes and terminal states.

With a 100,000-action limit, the policy reached the goal in 1,893 of 2,000 easy-map trials (94.65%). It used a mean of 27,703.8 executed actions and 7,066.3 collisions per easy-map trial, counting capped trials too. It solved all four easy maps in 405 of the 500 shared-sequence trials.

This does not make it a fair competitor to an LLM. It demonstrates a property of the protocol: a low decision count can conceal a very large execution budget. For future comparisons, I would report success as a function of both planning decisions and motor actions, alongside exploration coverage and collisions.

8 What should we test next?

These results come from four fixed easy mazes per model/configuration and a separate four-map Astra extension. There is one recorded run per configuration and case. The experiment is small, source aliases do not guarantee immutable model snapshots, and the native/API settings are not fully matched.

The next experiments should separate the factors that this pilot combines:

  • Mirror versus matte walls on the same graph, seed, budget, and model configuration.
  • Matched graph size and distance across tilings, with more seeds and repeated runs.
  • Matched conversation-state handling for native and direct-API agents, with the same prompts and reasoning settings.
  • Joint planning and action budgets, including visibility-free policies and collision-aware baselines.

A useful reference is an ideal local observer with exact memory. On these tree mazes, a conservative depth-first exploration policy can backtrack on known routes, enter a new cell, and scan its directions in one batch. It needs at most one decision per cell: 49/127 on the easy maps and 121/331 on the medium maps. The scan rotations still count as motor actions. The bound assumes the complete scan is available. It is an ideal-information reference, not a verified guarantee under the client's image-pruning policy or a measured human score.

The goal of this project is to make the navigation problem and the failure modes inspectable. The interesting question is how perception, remembered state, and exploration strategy fit together across a sequence of decisions.

Try the environment and API

The implementation is available in a private testing repository. The Python interface supports initialization, rendering, single actions, and action sequences, using the same canonical rules as the browser environment.

from mirror_maze import MirrorMaze

with MirrorMaze(topology="hex", difficulty="medium",
                seed="MIRROR-042") as maze:
    png = maze.render(width=1280, height=720)
    outcome = maze.perform(["right", "forward"],
                           stop_on_collision=False)
